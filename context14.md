# happy_tandemista — контекст разработки

Снимок состояния на 2026-08-12, чтобы продолжить работу с другой машины.
Читается вместе с `README.md` (как запускать) и `docs/superpowers/specs/2026-08-11-happy-tandemista-design.md` (полный дизайн).

## Что это за продукт

Сервис для дропзоны: автоматически собирает видео тандем-прыжка с носителей, метчит с клиентом,
анализирует, монтирует и отдаёт готовые ролики — по образцу FreeFallFilms, Shred Video, Team Cutaway.
Сегодня этот процесс ручной: оператор перекидывает файлы с карт, ищет чьи они, монтирует в редакторе —
часы работы на каждый прыжковый день.

Стратегия: сначала пилот на своей дропзоне, затем SaaS для многих. Поэтому развёртывание
single-tenant, но у всех сущностей есть `dropzone_id` и ничто не блокирует мульти-тенантность.

## Решения, принятые владельцем продукта

Это не догадки — это то, что было согласовано явно. Менять только по новому решению.

- **Сбор**: оба пути — станции с картридером и Wi-Fi-автовыгрузка с камер. Аплоадер ставится
  на любое число компьютеров дропзоны (манифест, каждый оператор), не на одну станцию.
- **Метчинг видео с клиентом**: авто-предложение (время + манифест + владелец камеры) плюс
  подтверждение оператора одним кликом.
- **Источники ролика**: всегда интервью на земле + прыжок + съёмка приземления; handcam и внешний
  оператор в разных комбинациях.
- **Монтаж**: авточерновик, затем ревью оператора перед публикацией.
- **Вычисления**: всё в облаке.
- **Доставка**: купившим видеопакет — сразу всё; остальным — превью с вотермарком и оплата постфактум.
- **Манифест**: свой мини-манифест в продукте; интеграции с внешними системами (Burble и т.п.) позже.
- **Оплата**: абстракция `PaymentProvider`, адаптеры ЮKassa (РФ, 54-ФЗ) и Stripe (США/мир),
  мультивалютность; PayPal в бэклоге.
- **Аплоадер**: десктоп для Windows и macOS из одной кодовой базы (рекомендация — Tauri).
- **Хранилища**: аплоадер сам складывает материал в настроенные хранилища дропзоны
  (Яндекс.Диск и/или сетевой диск и/или S3) через абстракцию `StorageBackend`; пайплайн забирает оттуда же.
- **Варианты монтажа на прыжок** (актуальный список, 4 штуки):
  `full_16x9` (~2–4 мин), `emotions_16x9` и `emotions_9x16` (~60–90 с, один монтаж в двух формах),
  `highlights_9x16` (15 с для сториз).
- **КЛЮЧЕВОЕ — CV своя, без LLM на инференсе.** Вызов облачной vision-модели на каждый кадр
  структурно неверен для этого продукта: ~300 кадров на прыжок × десятки прыжков в день = расходы,
  растущие линейно с оборотом. Первая реализация использовала адаптер к Claude Vision и была
  отвергнута целиком. Путь: сейчас свой локальный конвейер на OpenCV → копим размеченные данные
  с правок оператора на ревью → обучаем собственную модель и подставляем через тот же
  Protocol `CVAnnotator`. Инференс CPU-first, GPU только как ускоритель.
- **Бэклог, не блокировать архитектурно**: личный кабинет дропзоны с кастомизацией шаблонов и
  брендинга, инструменты допродаж, редактор шаблонов, интеграции манифест-систем.

## Что уже сделано: движок (этап 1 из 4)

Ветка `engine-core` влита в `main`, плюс ветка `emotions-vertical`. 31 коммит, 54 теста зелёных
(1 skipped — интеграционный тест реального GoPro-файла ждёт образца).

Работающая команда:

    tandemista <папка_прыжка> --out <папка> [--height N] [--no-cv]

Роли файлов определяются по префиксу имени: `interview_`, `handcam_`, `outside_`, `landing_`
(регистр расширения любой — GoPro пишет `.MP4`). На выходе четыре ролика.

### Как устроен конвейер

    файлы прыжка
       ├─ gpmf.py      телеметрия GoPro (GPS5 → высота, вертикальная скорость)
       ├─ media.py     ffmpeg-обёртки: длительность, аудио-RMS, кадры, наличие звука
       └─ frames.py    признаки кадра на OpenCV: резкость, оптический поток, яркость, доля неба
              ↓
       phases.py       фазы по телеметрии (conf 0.8–0.95) и по звуку (0.6)
       cv.py           фазы и моменты по кадрам (0.5) — LocalCVAnnotator, без сети
              ↓
       timeline.py     фьюжн камер в общее время прыжка; SOURCE_RANK решает,
                       чей вариант фазы победит: telemetry(3) > role(2) > audio(1) > cv(0)
              ↓
       templates.py    декларативные шаблоны: слоты «интервью 15–25 с», «отделение обязательно» и т.д.
       edl.py          заполнение слотов лучшими кусками → EDL
              ↓
       render.py       ffmpeg: нормализация fps/звука, letterbox под формат, склейка

### Инварианты, которые легко сломать

- **Два времени.** Фазы таймлайна — в общем времени прыжка; `Moment.t` и `Clip.src_in/src_out` —
  в локальном времени файла. Перевод: `jump = local + clock_offset`. В `edl.py` конверсия
  применяется ровно один раз в каждую сторону; тест `test_moment_with_nonzero_offset` это стережёт.
- **Подрезка перекрытий.** Два слота из одного файла не должны пересекаться — иначе зритель
  дважды увидит один кусок (эффект перемотки). `generate_edl` ведёт занятые интервалы по каждому
  файлу и сдвигает начало клипа. Клипы из РАЗНЫХ файлов пересекаться могут — это нормальная
  многокамерная съёмка.
- **Центрирование по моменту** не должно выносить клип за границы фазы; окно зажимается.
- **Пороги относительные**, а не абсолютные: перцентили внутри файла, нормировка на пик файла.
  Камеры и погода слишком разные для зашитых констант.
- **Ничего не теряется молча**: нечитаемый файл пропускается с диагностикой, сбой одного варианта
  не мешает остальным, файл без звука уходит в CV, а не считается битым.

## Ограничения этапа (важно перед реальными съёмками)

Движок проверен только на синтетике. Полный список — в `README.md`, здесь коротко:

1. **Тайминг телеметрии приблизительный.** Метки считаются по фиксированной частоте пакетов
   вместо реальной разметки `STMP`/`TSMP`, на длинной записи расхождение растёт до десятков секунд.
   Нет проверки захвата GPS — мусорная высота на наборе может выдумать «свободное падение».
   HERO11+ пишет `GPS9` вместо `GPS5`, для них телеметрия сейчас не читается вовсе.
   **Это задача №1 следующего этапа, и чинить её честно можно только на настоящих файлах.**
2. **Один прыжок на файл, один файл на роль.** Смещения часов в CLI — заглушки (±3600 с) до этапа
   метчинга. Карта с несколькими прыжками смонтирует произвольный; запись, разбитая камерой на
   части (файл больше 4 ГБ), может взять кусок не из той части.
3. **Не оптимизировано под большие файлы.** Анализ декодирует каждый кадр в полном разрешении,
   рендер режет фильтром вместо перемотки — час 4K60 займёт недопустимо долго.
4. **CV-эвристики опираются на видимое небо** — в пасмурную погоду слабеют.

## Что дальше по плану

1. **Реальные файлы прыжка** — до всякой новой разработки. Один настоящий тандем покажет про
   телеметрию и качество монтажа больше, чем этап разработки вслепую.
2. **Облачный каркас**: FastAPI, PostgreSQL, Celery/Redis, `StorageBackend`, админка ревью,
   клиентская страница.
3. **Аплоадер** (Tauri, Windows + macOS), автометчинг, калибровка `clock_offset`.
4. **Доставка и оплата**: рассылка ссылок, вотермарки, `PaymentProvider` (ЮKassa, Stripe).
5. **CV со своими весами**: сначала слой детекции лиц и мимики на открытых весах
   (YuNet ONNX ~230 КБ, MediaPipe Face Landmarker ~3.7 МБ; качать скриптом в `backend/models/`,
   в git не класть), затем обучение собственной модели на разметке из правок оператора.

## Как работали (метод, который стоит сохранить)

Разработка шла по скиллам superpowers: brainstorming → spec → план по задачам → исполнение
сабагентами с обязательным ревью каждой задачи и финальным ревью всей ветки.

Что это дало на практике — ревью ловило дефекты, которые зелёные тесты пропускали:

- парсер GPMF брал коэффициент высоты от чужого сенсора (на реальном файле высота была бы
  молча неверной);
- оценка «красивых кадров» упиралась в потолок и переставала различать кадры;
- слот отделения целиком попадал внутрь слота падения — зритель увидел бы перемотку;
- камера без звука отбрасывалась как «битая» вместо анализа через CV;
- горизонтальный рендер растягивал вертикальные и 4:3 источники.

Вывод для будущих сессий: **зелёные тесты ничего не доказывают, если тест писал тот же, кто код.**
Отдельная стадия ревью с указанием, что именно проверить, окупается.

Ещё одна деталь: планы и спеки лежат в `docs/superpowers/`, рабочие заметки исполнения —
в `.superpowers/` (в `.gitignore`, в репозиторий не попадают).

## Настройка на новой машине

    git clone <url> && cd happy_tandemista/backend
    python3 -m venv .venv && source .venv/bin/activate
    pip install -e ".[dev]"
    pytest          # ожидается 54 passed, 1 skipped

Нужен `ffmpeg`/`ffprobe` в PATH (`brew install ffmpeg`). Python ≥ 3.12.
Зависимости рантайма ровно две: `numpy` и `opencv-python-headless`. Не добавлять третью без
обсуждения — и в частности никаких SDK облачных vision-моделей: это нарушит ключевое решение.
